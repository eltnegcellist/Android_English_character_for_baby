# 追加検証：CMU辞書を使う別候補

**固定発話・設定済みの日本語名の変換は改善した。アプリ統合はまだ承認しない。**

## 今回変更したもの

検証環境だけで、次の別候補を作った。前回の検証結果は保持している。

1. Misaki 0.9.4の英語処理コードを選択して使用する。出所の詳細を確認できなかったMisakiのgold/silver辞書は一切含めない。
2. 辞書をCMUdictへ交換する。公式リポジトリのcommitとSHA-256を固定し、ライセンス本文を同梱する。
3. LGPLのnum2wordsを使わず、独立して書いた数値読み変換を使う。
4. 設定から渡された日本語名のローマ字に限って、専用の近似音素変換を使う。一般の未知英単語には適用しない。
5. Misaki固有の記号をKittenのIPA記号へ展開する。未知記号を黙って削除しない。

VAD、ASR、会話制御、UI、モデルダウンロード、現在のKittenSpeakerは変更していない。

## 実行結果

| 検査 | 件数 | 今回の結果 |
| --- | ---: | --- |
| 固定発話データ | 202 | 未解決語・Kitten非対応記号ゼロ |
| 設定された名前を挿入するケース | 780 | 未解決語・Kitten非対応記号ゼロ |
| 最初の基礎テスト文 | 12 | 全件変換可能 |
| 数値読みの期待値 | 26 | 26件一致、結果の英単語も全件音素化可能 |
| 名前の近似発音規則 | 7 | 定義した音素列と一致 |
| Kitten向け記号展開 | 8 | 定義した期待値と一致 |
| コーパスにない英文 | 20 | 全件変換可能（自由文全体の網羅性を証明するものではない） |
| 明確なbassの文脈 | 4 | 音楽3例・魚1例で期待値と一致 |
| 未知語・未対応入力・曖昧な意味の検出 | 16 | 全件、規定どおり拒否／未解決検出 |

上の期待値試験は合計61項目。発話データを通したケース数とは別集計。

780ケースはHana、Hana-chan、Aoi-chan、Haruto-chan、Tsumugi-chanの5種類を、156件の返答テンプレートへ挿入したもの。任意の名前が対応済みという意味ではない。名前以外の未知語を日本語名として推測しない。

初回の8件の読み分け比較は削除していない。read、wind、tearなど7件は一致し、`The bass is low.` は指定された音楽の読みを自動で確定できない。今回はこの文を「意味が未解決」と検出し、読み上げ用IPAを返さない。`bass guitar`、`bass clef`、`double bass`と、魚が泳ぐ文は別に試験している。この少数の文脈規則は、一般的な語義判定の完成を示さない。

名前の直後の`!`をspaCyがNNPと誤判定する1ケースも検出した。句読点だけからなる未解決トークンは、その句読点を保持する。英単語の未解決をこの処理で隠さない。

## ライセンスと出所

- CMUdict: `cmusphinx/cmudict`、commit `74790861f652b15e4ac49015a90074ad62a27690`。辞書SHA-256は `81917843c7f44ce2b094ac63873c2c7a4cf802040792c455ba3ca406891c3d22`。公式LICENSEの再配布条件を保持する。
- 選択したMisakiコード: Apache-2.0。元ファイルと変更後ファイルのSHA-256は`candidates/source-manifest.json`に記録。変更は数値処理のimport差替え。
- CMU辞書にないpeekaboo、pitter、mmm、短縮形の補助音素、およびused-toの音素は、検証用に独立定義した。Misaki辞書やeSpeakの生成結果をコピーして補完していない。これらは音声での品質検証が必要。
- クリーン環境のパッケージメタデータ検査ではGPL／LGPL表記の検出ゼロ。num2words、元のMisaki配布パッケージ、phonemizer、espeakng-loaderはインストールされていない。
- これは検証環境と選択した資材の検査結果。最終APKが非GPLであることの証明ではない。

Misaki元辞書の調査では、公開履歴の最初の投入が`7be11d0806b6fdb61513e11769928cbae2560c1e`のEnglish baselineであることまでは確認した。詳細な辞書作成元の記載を確認できなかったため、今回の候補では元辞書を使用しない判断とした。「元辞書はGPL」と断定したわけではない。

## 安定版との関係

検証基準はv1.9.12 / `62f39abc095dd29a57d86a0efdef5400a2bb4293`。今回、更新されたmainの`09ef60737479fe234f7fea617efd0eca2f409418`とも比較し、LiteResponseEngineとLiteSpeechStyle、および抽出した発話データが一致することを確認した。

前回のMisaki候補と比べると、202件中172件で音素文字列が変わっている。アクセント、弱形、flapなどの違いを含む。**文字列が正常になったことから、現在の安定版と同じ音質だとは判断できない。** この比較相手は初回のMisaki候補であり、安定版Sherpa音声そのものではない。

## 残る条件

| 条件 | 状態 |
| --- | --- |
| LGPL数値処理への依存 | 今回の候補では除外 |
| Misaki元辞書への依存 | 今回の候補では除外、CMUへ交換 |
| Lite固定発話の字句・記号カバレッジ | 今回の202件で通過 |
| 設定された5種類の名前の変換 | 今回の780ケースで通過 |
| 日本語名の自然さ、任意の名前 | 未合格。英語TTS向け近似で、外国語名等は未対応 |
| 全発話の正しい発音、Full自由文 | 未合格。少数の例と辞書カバレッジだけでは証明できない |
| 音質・Kiki・speed 0.8の維持 | 未検証 |
| Android実装・停止・コールバック・耐久 | 未検証 |
| 最終APK内容 | 未検証。APKは作成していない |

今回の名前処理は、発話文とは別に「これは設定された日本語名」という情報を受け取る。現在のspeak(text)と同じ契約で、TTS部分だけからその情報を取得する設計はまだ検証していない。

## 再実行

Python 3.12の別環境に`candidates/requirements-clean.lock`をインストールする。元のMisaki配布物やnum2wordsは不要。

```bash
python -m pip install -r tts-validation/candidates/requirements-clean.lock
python tts-validation/candidates/fetch_cmudict.py /tmp/mitsukotoba-cmu-data
python tts-validation/validate_clean_candidate.py --dictionary /tmp/mitsukotoba-cmu-data/cmudict.dict
```

辞書とLICENSEは固定SHA-256で検査する。最後のスクリプトは統合未承認を表すexit code 1を返す。実測詳細は`cmu-candidate.json.gz`、集計は`cmu-candidate-summary.json`。

次は、実際の発話について発音の期待値を広げ、名前・未知語・曖昧語の扱いを確定する。G2Pの合格条件が揃うまではONNX単体エンジン、アプリ統合、実機APKへ進まない。
